# 연구 세션 절차

연구 프로젝트에서 세션을 시작하고 마치는 절차와, 모든 연구 스킬이 따르는 공통 규칙을 정한다. 도구가 하나인 프로젝트와 둘인 프로젝트에 같은 절차를 쓴다. 프로젝트를 새로 만드는 일은 research-scaffold가 맡는다.

## 0. 공통 규칙

다른 연구 스킬은 이 규칙을 "공통 규칙"으로 가리키고 되풀이하지 않는다. 프로젝트 규칙(`AGENTS.md`, 설정)은 스킬의 절차보다 앞서지만 공통 규칙 3, 8, 9, 10보다 앞서지 않는다.

1. 기억이나 앞 대화가 아니라 파일을 읽고 시작한다.
2. 시각은 시계(`date`)에서 읽는다. 어림으로 적지 않는다.
3. 만든 쪽이 채점하지 않는다. 검산과 심사는 새로 띄운 에이전트가 하고, 앞선 대화를 넘기지 않는다. 사실 대조와 인용 검증은 원고를 고친 에이전트가 아닌 쪽이 한다. 따로 띄울 에이전트가 없으면 총괄이 하되, 고친 쪽이 총괄이었으면 그 사실을 보고에 적는다.
4. 에이전트가 낸 숫자는 총괄이 다시 계산한 뒤 문서에 넣는다.
5. 에이전트 호출이 실패나 거절로 표시돼도 저장소와 파일을 확인한 뒤 보고한다. 실제로는 커밋을 만든 경우가 있다.
6. 사용자만 하는 일(제출, 공개 저장소 push, 계정과 보안 설정, 되돌릴 수 없는 결정)은 직전 단계까지만 준비한다. 계획 승인과 실행 승인은 다르다.
7. 총괄이 사용자 대신 정한 것은 대리 판정으로 적고 대기열(`docs/승인기록.md`의 대리 판정 절)에 넣는다. 세션을 마칠 때 남은 수를 알린다.
8. 결과와 숫자는 숨기거나 바꾸지 않는다. 원고에서 약점을 필요 이상으로 고백하지 않는다. 불리한 결과에는 범위를 깎기 전에 설계로 답할 방법을 먼저 찾는다.
9. 결과를 본 뒤에는 고정한 기준을 바꾸지 않는다. 바꿔야 하면 사용자가 정하고 승인기록에 남긴다.
10. 사실이 아닌 기록을 남기지 않는다. 하지 않은 일, 보내지 않은 것, 확인하지 못한 것은 그렇다고 적는다.
11. 만들거나 고친 파일은 답에서 바로 열 수 있게 보인다(환경이 지원하면 링크).
12. 글은 국문 학술 문체(korean-academic-style)와 용어집을 따른다. 영문은 english-academic-style을 따른다.

## 1. 시작할 때

1. 원격 저장소가 있으면 `git pull --rebase origin main`. 충돌이 나면 상대 것을 살리고 내 것을 다시 적는다. 공개 저장소를 하위 폴더로 두는 구조면 그 저장소도 pull한다.
2. 프로젝트 설정(`docs/설정.md`)을 읽는다. 도구, 역할과 모델, 원고, 지킬 것이 여기 있다. 없으면 기본값을 쓰고 그렇게 했다고 말한다.
3. 현황(`00-교류/현황.md`)을 읽는다. 어느 문서의 어느 판이 현행이고 누가 맡는지는 여기가 기준이다.
4. 세션 기록(`00-교류/log/`)에서 최근 세 파일을 읽는다.
5. 자기 앞으로 온 인계 노트 가운데 `status: 대기`를 읽고 `확인`으로 바꾸고 `read:`에 날짜를 적는다. 요청은 이번 할 일에 넣는다.
6. `git log --oneline -20`으로 다른 도구의 커밋을 본다.
7. 할일목록과 승인기록(대리 판정 대기열 포함)을 본다. 사용자 확인이 남은 것이 있으면 먼저 알린다.

## 2. 일하는 동안

- 현황의 담당 칸에 적힌 쪽만 그 문서를 고친다. 담당이 아니면 심사와 의견까지만 낸다.
- 새 판을 만들면 지난 판은 같은 폴더의 `구판/`으로 내린다. 지우지 않는다.
- 커밋은 작업 단위마다 한다. 여러 세션이 같은 폴더를 함께 고칠 수 있으므로 `git add -A`를 쓰지 않고 바꾼 파일만 더한다.
- 다른 도구가 만든 파일을 지우거나 옮길 때는 인계 노트에 적는다.
- `.env`, 키 파일, 원자료(`data/raw/`, `results/raw/`)는 커밋하지 않는다.
- git 이력을 고쳐 쓰지 않는다. 잘못되면 되돌리는 커밋을 새로 만든다. 이력 정리가 필요하면 사용자가 정한다.

## 3. 마칠 때

1. 다른 도구가 있는 프로젝트에서 바꾼 것이 있으면 인계 노트 한 장을 쓴다(5절 양식).
2. 현황을 갱신한다. 현행 판이 바뀌었으면 반드시.
3. 세션 기록 파일 하나를 남긴다(5절 양식).
4. 이번 세션의 사용자 결정을 승인기록에 시각과 함께 적는다. 대리 판정은 따로 표시한다.
5. 도구 이름을 접두로 붙여 커밋한다(예: `[claude]`). 접두는 프로젝트 설정의 도구 목록을 따른다.
6. 비공개 저장소는 push한다. 거절되면 pull --rebase 뒤 다시 한다. force push는 하지 않는다. 공개 저장소의 push는 사용자 확인 뒤에 한다.
7. 사용자에게 남은 일과 대리 판정 대기 수를 알린다.

## 4. 도구가 하나일 때와 둘일 때

- 도구가 하나면 인계 노트 폴더를 만들지 않고 세션 기록만 남긴다.
- 두 번째 도구는 반론자로 쓸 때 가장 쓸모가 있었다. 관문 판정이나 원고 심사에서 반박을 맡길 때 인계 노트에 무엇을 반박할지, 무엇을 받지 않는지(앞선 대화, 이전 심사평)를 적는다.
- 두 번째 도구가 한동안 쉬면 현황에 그 사실을 적고, 그 도구가 담당이던 문서의 담당을 다시 정한다.

## 5. 양식

세션 기록 `00-교류/log/YYYY-MM-DD-NN-<도구>.md`:

```
---
date: YYYY-MM-DD
who: <도구>
commit: <이 세션의 마지막 커밋, 저장소가 둘이면 둘 다. 없으면 미커밋>
note: <인계 노트 경로, 없으면 없음>
---
(한두 줄. 무엇을 했고 다음에 무엇이 남았나)
```

인계 노트 `00-교류/<보낸 도구>-to-<받는 도구>/YYYY-MM-DD-NN-<주제>.md`:

```
---
from: <보낸 도구>
to: <받는 도구>
date: YYYY-MM-DD
commit: <직전 커밋>
status: 대기
read:
---
## 무엇을 했나 (판단 근거 포함)
## 바뀐 파일
## 상대에게 요청
## 사용자 판단이 필요한 것 (하지 않은 것도 적는다)
```

## 6. 옛 규약 프로젝트 옮기기

`00-교류/LOG.md` 한 파일에 줄을 쌓던 프로젝트를 이 절차로 옮긴다.

1. `00-교류/log/`를 만들고 `README.md`(5절 양식)를 둔다.
2. `LOG.md`는 지우지 않고 `00-교류/구판/LOG.md`로 내린다. 옮긴 날을 현황에 적는다.
3. `AGENTS.md`(또는 도구별 규칙 파일)의 세션 절차를 이 스킬을 가리키는 한 줄로 바꾼다.
4. 인계 노트 폴더는 그대로 둔다.
5. 옮긴 사실을 인계 노트와 세션 기록에 적는다.

## 7. 환경 문제

| 문제 | 대처 |
|---|---|
| 연결 폴더에서 삭제가 막혀 git이 잠금 파일(`index.lock`, `HEAD.lock`, `tmp_obj_*`)에서 멈춘다 | 폴더 삭제 권한을 한 번 요청한다. 받지 못하면 잠금 파일을 `_to_delete/`로 옮기고 현황에 적는다 |
| `sed -i`, `perl -i`가 `.fuse_hidden*` 파일을 남긴다 | 파이썬으로 같은 파일에 덮어쓴다. `.gitignore`에 `.fuse_hidden*` |
| 연결 폴더 셸에 GitHub 인증이 없다 | 커밋을 `git bundle`로 묶어 인증이 있는 환경으로 옮기고 거기서 push한다 |
| 클라우드 작업 공간이 잠들거나 사라진다 | 배치가 끝날 때마다 결과를 연결 폴더에 쓰고 bundle을 남긴다 |
| 대소문자만 다른 파일 이름이 겹친다 | 파일 이름을 바꾸고 현황에 적는다 |
| 출판사나 학회 사이트에 닿지 못한다 | 추측하지 않고 "확인하지 못함, 가정"으로 적고 사용자에게 요청한다 |
