# 09. 진행 보이기

에이전트에게 일을 맡기면 사용자는 화면 밖에서 무슨 일이 일어나는지 모른다. 몇 분 동안 아무 표시가 없으면 사용자는 에이전트가 멈췄다고 의심하고, 일을 끊거나 다시 시키고, 같은 일이 두 번 돈다. 보고의 모양이 프로젝트마다 다르면 매번 읽는 법을 새로 익혀야 한다. 이 문서는 모든 스킬이 같은 틀로 진행을 보이는 이유와 예시를 적는다. 규범은 `research-session` 8절, 복사할 양식은 `templates/진행판.md`에 있다.

## 1. 원칙

1. 같은 틀을 쓴다. 시작 안내, 진행판, 마침 보고의 세 틀과 일곱 상태어를 어느 프로젝트, 어느 세션, 어느 도구에서든 같게 쓴다. 사용자는 첫 줄과 왼쪽 이름 칸만 보고 어디를 읽을지 안다.
2. 먼저 말한다. 일을 시작하기 전에 무엇이 생기고, 어떤 순서로, 얼마나 걸리고, 사용자가 언제 무엇을 해야 하는지 보인다. 사용자는 자리를 떠도 되는지 그 자리에서 판단할 수 있다.
3. 침묵하지 않는다. 사용자가 보는 곳에 5분 넘게 아무 표시도 없게 두지 않는다. 기다리는 동안에는 무엇을 기다리는지, 언제 다시 알릴지를 적는다.
4. 숫자로 보인다. 진척은 항목 수로 센 막대, 시각은 시계에서 읽은 값, 어림은 분 단위로 적는다. 어림을 넘기면 넘겼다고 적는다.
5. 상태를 꾸미지 않는다. 응답이 없는 에이전트를 `[진행]`으로 두지 않는다. 바뀐 파일이 많다고 진행이 많은 것이 아니다.

## 2. 상태어

| 상태어 | 뜻 | 반드시 붙일 것 |
|---|---|---|
| `[예정]` | 아직 시작하지 않음 | 선행 항목 |
| `[진행]` | 지금 하고 있음 | 마지막 신호 시각, 셀 수 있으면 진척 |
| `[대기]` | 에이전트, 명령, 외부 응답을 기다림 | 무엇을, 어림, 다음 알림 시각 |
| `[막힘]` | 이대로는 나아갈 수 없음 | 이유, 풀려면 필요한 것 |
| `[멈춤]` | 멈춤 선이나 사용자 결정 때문에 세움 | 무엇을 정해야 하나 |
| `[완료]` | 끝남 | 결과 한 줄, 확인 상태 |
| `[건너뜀]` | 하지 않기로 함 | 이유 |

`[대기]`와 `[막힘]`을 가르는 기준은 시간이 해결하는지다. 에이전트가 돌아오면 풀리는 것은 대기, 사용자나 환경이 무언가를 해 주어야 풀리는 것은 막힘이다. `[멈춤]`은 멈춤 선이나 사용자 결정, 사용자 검토 때문에 일부러 세운 것이다. 앞 항목이 끝나기를 기다리는 것은 `[예정]`이다. 응답이 없는 에이전트는 어림을 넘기고 5분이 더 지나면 `[대기]`, 다시 띄워도 응답이 없으면 `[막힘]`이다(research-session 8.3).

## 3. 예시

### 3.1 한 세션의 일

시작 전에 보인다.

```
== 시작 | demo-study | 선행 연구 정찰과 G0 판정 | 14:02 ==
지금   : 문제 정의 v3 잠금, 결정 대기 0, 대리 판정 대기 1, 검토서 0
목표   : 정찰 문서 1편과 G0 관문 기록 1건
순서   : 1 검색어 확정 --> 2 정찰 (2a 학회 || 2b 프리프린트) --> 3 거리 판정
         --> 4 독립 검산 --> 5 G0 판정
어림   : 45분 (1 5, 2 20, 3 10, 4 5, 5 5)
사용자 : 5에서 판정 확인 1건. 그 전에는 자리를 떠도 된다
멈춤   : 거리 1 논문이 나오면 3에서 멈추고 알린다
```

에이전트 둘을 띄운 직후와 하나가 돌아왔을 때 보인다.

```
== 진행 | demo-study | 선행 연구 정찰과 G0 판정 | 14:19 (시작 14:02, 경과 17분, 남은 어림 28분) ==
전체   [####--------] 2/5  40%
단계   1 검색어 [완료]  2 정찰 [진행]  3 거리 판정 [예정]  4 검산 [예정]  5 G0 [예정]

에이전트    역할        맡은 일              상태     시작   마지막 신호  진척
scout-a     문헌 정찰   학회 3곳, 2019~      [완료]   14:07  14:18        후보 41
scout-b     문헌 정찰   프리프린트           [진행]   14:07  14:19        34/80
checker     독립 검산   거리 판정 재검토     [예정]   -      -            3 뒤

최근   14:18 scout-a 끝: 후보 41편, 거리 1~2 후보 3편
대기   scout-b, 어림 6분, 14:25에 다시 알림
결정   없음
```

끝낼 때 보인다.

```
== 끝 | demo-study | 선행 연구 정찰과 G0 판정 | 14:51 (걸린 시간 49분, 어림 45분) ==
결과   : 후보 112편, 거리 1 0편, 거리 2 4편. G0 문자 판정 통과
확인   : 독립 검산 거리 판정 16건 재검토, 불일치 1건(거리 2에서 3으로 조정)
바뀐 것: 파일 3개 (아래 링크)
남은 것: G0 종합 판정 확인 1건, 할 일 0건
다음   : G2 단순 대안의 짧은 실행
```

### 3.2 어림을 넘겼을 때

```
== 진행 | demo-study | 시뮬레이션 재실행 | 15:40 (시작 15:10, 경과 30분, 어림 20분을 넘김) ==
전체   [######------] 3/6  50%
단계   1 준비 [완료]  2 실행 [진행]  3 집계 [예정]

최근   15:38 실행 2가 어림 20분을 50% 넘김. 로그는 매분 늘고 있음(마지막 15:39)
대기   실행 2, 남은 반복 140/400. 이 속도면 25분 더. 15:45에 다시 알림
결정   없음. 16:10까지 끝나지 않으면 반복을 200으로 줄일지 묻겠다
```

### 3.3 사용자가 자리를 비운 동안

검토서의 진행 칸을 같은 상태어로 쓴다. 마지막 신호가 30분 넘게 지난 `[진행]`은 멈춘 것으로 본다.

```
항목  상태     커밋      시작   마지막 신호  진척
W1    [완료]   a1b2c3d   23:05  23:41        시험 12/12
W2    [진행]   -         23:42  01:10        수집 3,200/5,000
W3    [예정]   -         -      -            W2 뒤
```

### 3.4 여러 프로젝트

research-portfolio의 현황판도 같은 상태어와 막대를 쓴다.

```
== 진행 | 포트폴리오 | 일일 점검 | 08:30 ==
편        단계        전체 진척               다음 관문    마감      상태
study-a   원고        [#########---] 9/12     -            D-12      [진행]
study-b   관문        [##----------] 2/10     G2           -         [멈춤] 결정 1건
study-c   맡김 검토   [######------] 3/6      -            -         [멈춤] 검토서 1건
```

## 4. 도구별 주의

- 도구에 작업 목록 위젯이 있으면 진행판의 단계와 같은 이름으로 올린다. 위젯은 대기 이유와 숫자를 보이지 못하므로 진행판을 대신하지 않는다.
- 에이전트 호출이 끝날 때까지 화면을 붙잡는 도구에서는 호출 직전에 어림과 다음 알림 시각을 보인다. 여러 에이전트를 함께 띄울 수 있으면 함께 띄우고, 배경으로 돌릴 수 있으면 배경으로 돌린다.
- 대화 중간의 글이 사용자에게 요약되어 보이는 도구에서는 진행판을 사용자에게 그대로 보이는 경로(메시지 도구 등)로 보낸다.
- 코드 블록이 고정폭으로 보이지 않는 곳에서는 표(markdown)로 같은 칸을 보인다. 칸의 순서와 상태어는 바꾸지 않는다.
