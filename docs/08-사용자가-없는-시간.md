# 08. 사용자가 없는 시간

에이전트는 사용자가 자리를 비운 동안에도 일할 수 있다. 밤, 회의와 강의, 주말, 이동 시간이 모두 그렇다. 이 체계는 그 시간을 따로 운영하지 않고 세션의 끝과 시작에 붙인다. 사용자가 자리를 뜨기 전에 맡길 일을 정하고, 돌아오면 그동안의 결과부터 검토한다. 사용자의 시간은 결정, 틀, 검토에 쓰고 조사, 구현, 검산은 사용자가 없는 시간으로 옮기는 것이 목적이다.

절차는 `research-batch` 8절, 세션과 잇는 곳은 `research-session` 1절과 3절에 있다. 양식은 `templates/맡김지시서.md`, `templates/검토서.md`, `templates/맡김-예약프롬프트.md`다.

## 1. 한 바퀴

| 때 | 하는 일 | 남는 파일 |
|---|---|---|
| 자리를 뜨기 전 | 세션을 마치며 총괄이 맡길 일을 제안하고, 사용자가 맡김 지시서를 승인한다 | `docs/맡김/<시작>-지시서.md`(main) |
| 자리를 비운 동안 | 에이전트가 지시서대로 일하고, 다른 에이전트가 확인하고, 사용자가 돌아오기 전에 검토서를 쓴다 | 결과 파일, `away/<시작>` 브랜치, `docs/맡김/<시작>-검토서.md` |
| 돌아와서 | 세션을 시작하며 `away/` 브랜치의 검토서부터 본다. 항목마다 받음, 돌려보냄, 버림을 정하고 결정 대기에 답한다. 받은 항목과 검토서를 main으로 가져온다 | 검토서의 사용자 표시, 승인기록, `docs/맡김/지표.md` |

하루 한 번 밤에 돌리면 낮에 결정하고 밤에 일하는 순환이 된다. 점심 회의 두 시간에 짧게 맡겨도 같은 절차다. 맡김이 길수록 지시서의 갈림길과 멈춤 선을 더 자세히 적는다. 이 문서에서 짧은 맡김은 4시간 이하를 말한다.

## 2. 원칙

### 2.1 사용자가 없는 동안에는 틀을 바꾸지 않는다

맡긴 작업은 잠근 문제 정의, 봉인한 기준, 관문 판정, 사용자가 승인한 주장 목록 안에서만 한다. 틀을 흔드는 발견(가장 가까운 선행 연구가 거리 1로 보임, 결과가 가설과 반대, 단순 대안이 이김)은 고치지 않고 검토서의 결정 대기 맨 위에 올린다. 사용자가 돌아와서 problem-grill이나 feasibility-gate로 다룬다.

깨지면. 사용자가 없는 동안 연구의 방향이 바뀌고, 돌아와서 받은 결과가 승인한 계획과 다른 질문에 답한다.

### 2.2 갈림길은 떠나기 전에 정한다

물어볼 사람이 없다. 지시서에 예상되는 갈림길을 "상황이면 할 일"의 꼴로 적는다(예: "수집이 크레딧 상한의 80%에 닿으면 표본을 절반으로 줄이고 계속한다", "구현이 시험을 두 번 통과하지 못하면 그 항목을 멈추고 다음 항목으로 간다"). 적지 않은 갈림길에서는 되돌릴 수 있는 쪽을 고르고 대리 판정으로 적거나, 그 항목만 멈추고 다른 항목으로 간다. 되돌릴 수 없는 쪽은 고르지 않는다.

### 2.3 맡기는 양은 검토 시간에 맞춘다

이 방식을 막는 것은 에이전트의 작업량이 아니라 사용자의 검토 시간이다. 에이전트는 사용자가 다 읽지 못할 만큼의 결과를 낸다. 검토하지 못한 결과는 쓸 수 없고, 쌓이면 다음 결정이 확인하지 않은 결과 위에 올라간다. 그래서 지시서에 검토 예산(기본 30분, 짧은 맡김이면 10분)을 적고, 검토서는 그 시간 안에 읽히는 분량으로 쓴다. 지난 검토서에서 아직 받지도 돌려보내지도 않은 항목(검토 대기)이 이번에 맡길 새 항목보다 많으면 새 일을 맡기지 않고 검토 대기를 줄이는 일(요약, 검산, 정리)만 맡긴다.

### 2.4 돌아오기 전에 확인을 끝낸다

맡긴 동안 나온 숫자, 인용, 구현은 만든 에이전트가 아닌 에이전트가 사용자가 돌아오기 전에 확인한다(공통 규칙 3). 검토서에는 항목마다 확인 상태(통과, 불일치, 미검산)를 붙인다. 미검산 숫자는 결론의 근거로 쓰지 않는다. 사용자가 돌아와서 할 일을 "맞는지 다시 확인"이 아니라 "받을지 정하기"로 줄이는 것이 목적이다. 다른 계열 도구가 있으면 마지막에 반론자로 넣는다.

### 2.5 받기 전까지는 갈라 둔다

맡긴 작업은 `away/<시작>` 브랜치에 커밋한다. `<시작>`은 지시서를 쓴 시각(`YYYY-MM-DD-HHMM`)이다. 지시서는 떠나기 전에 main에 두고, 결과와 검토서는 브랜치에 둔다. 사용자가 받은 항목만 main에 합치고, 돌려보내거나 버린 항목은 브랜치에 이력으로 남긴다. 그동안 다른 도구나 사용자가 main을 고쳐도 섞이지 않는다. 프로젝트 설정에서 main에 바로 커밋하게 바꿀 수 있지만, 그러면 검토가 "고르기"에서 "되돌리기"로 바뀐다.

### 2.6 멈춤 선을 숫자로 둔다

| 멈춤 선 | 기본값 | 닿으면 |
|---|---|---|
| 전체 마감 | 사용자가 돌아오는 시각의 1시간 전(짧은 맡김이면 15분 전) | 진행 중인 항목을 정리하고 검토서를 쓴다 |
| 같은 항목의 실패 | 2회 | 그 항목을 멈추고 다음 항목으로 |
| 쿼리 크레딧, API 비용 | 지시서에 적은 상한 | 크레딧을 쓰는 항목을 모두 멈춘다 |
| 확인 불일치 | 한 항목에서 1건 | 그 결과에 기대는 다음 항목을 시작하지 않는다 |

### 2.7 사용자가 없을 때 하지 않는 것

제출, 공개 저장소 push, 메일과 메시지 발송, 결과 파일과 원자료 삭제, 봉인한 사양의 수정, 봉인하지 않은 실험의 실행, 지시서에 없는 외부 서비스 가입이나 결제나 설치, 문제 정의와 주장 목록의 수정, `away/` 브랜치를 main에 합치기.

## 3. 무엇을 맡기나

맡기기 좋은 일은 기준이 이미 있고, 결과를 다른 에이전트가 확인할 수 있는 일이다.

| 맡기기 좋음 | 맡기지 않음 |
|---|---|
| 정해진 검색어로 하는 문헌 정찰과 거리 판정 초안 | 신규성의 최종 판정 |
| 봉인한 사양대로 하는 자료 수집, 집계, 시뮬레이션 | 사양을 정하는 일 |
| 시험이 있는 구현, 리팩터링, 재현 | 시험 기준이 없는 설계 |
| 원고의 독립 검산, 사실 대조, 모의 심사 바퀴 | 주장의 크기를 바꾸는 원고 수정 |
| 절삭 후보 표, 변경 기록 정리 | 큰 삭제의 결정 |

판단이 필요한 일을 맡기려면 떠나기 전에 판단을 기준으로 바꿔 둔다. 바꿀 수 없으면 그 일은 사용자가 있을 때 한다.

## 4. 흔한 실패

| 실패 | 신호 | 대처 |
|---|---|---|
| 검토 적체 | 검토 대기가 세 번 연속 는다 | 다음 맡김은 정리만 한다(2.3, research-batch 8.1 1번) |
| 틀의 표류 | 검토서에 승인하지 않은 주장이나 새 용어가 나온다 | 그 결과를 돌려보내고 지시서의 "바꾸지 않을 것"을 늘린다 |
| 오류의 누적 | 앞 항목의 불일치 위에 다음 항목이 올라간다 | 확인 불일치 멈춤 선(2.6)을 지킨다 |
| 첫 단계에서 멈춤 | 검토서가 비어 있고 진행 칸이 첫 항목에서 끝난다 | 예약 작업이 승인이나 인증을 기다렸는지 본다(5절). 처음 세 번은 짧게 시험한다 |
| 지어낸 문헌 | 확인 수준이 비어 있는 인용 | literature-scout의 확인 수준과 검색어 기록을 통과 조건에 넣는다 |
| 바쁘기만 한 맡김 | 바뀐 파일은 많은데 받을 만한 결과가 없다 | 진척은 받은 항목 수로 센다 |

## 5. 인프라 조건

- 사용자의 컴퓨터가 꺼져 있어도 돌아야 하면 저장소를 원격(GitHub 등)에 두고 클라우드 작업 공간에서 돌린다. 자료가 사용자 컴퓨터에만 있으면 그 컴퓨터를 켜 두고 작업에 붙인다.
- 지금 세션에서 바로 이어 돌릴 수도 있고, 예약 작업으로 나중에 시작할 수도 있다. 매일 같은 시각에 되풀이 예약하면 실행할 때마다 가장 최근의 승인된 지시서를 고르되, 돌아오는 시각이 지났거나 이미 검토했거나 모두 끝낸 지시서는 건너뛴다. 예약 작업은 매번 새 세션이므로 `templates/맡김-예약프롬프트.md`처럼 프롬프트만으로 시작할 수 있어야 한다.
- 예약 작업이 도구 호출마다 승인을 기다리면 첫 단계에서 멈춘다. 쓰는 동작이 승인 없이 돌도록 승인 설정을 정하거나, 승인이 필요한 동작(설치, 외부 쓰기)을 맡김에서 뺀다. 어느 쪽인지 지시서에 적는다.
- 한 세션이 끝까지 이어지지 않을 수 있다. 항목마다 커밋하고 검토서 초안의 진행 칸에 적어 두면 다음 실행이 끝나지 않은 첫 항목부터 잇는다.
- 비공개 저장소의 `away/` 브랜치 push는 사용자가 없을 때 해도 된다. main에 합치는 일은 검토 뒤에 한다.

## 6. 잘 돌아가는지 재는 법

검토서의 사용자 표시를 모아 `docs/맡김/지표.md`에 한 줄씩 쌓고, 일주일에 한 번 본다. 받은 비율이나 실제 검토 시간이 세 번 연속 기준을 벗어나면 다음 맡김의 항목 수를 줄인다. 확인 불일치가 늘면 지시서의 통과 조건과 확인 방법을 고친다.

| 지표 | 계산 | 기준(기본) |
|---|---|---|
| 받은 비율 | 받은 항목 / 끝낸 항목 | 60% 이상 |
| 실제 검토 시간 | 사용자가 적은 검토 시간 | 검토 예산의 1.5배 이하 |
| 확인 불일치 | 불일치 항목 / 확인한 항목 | 줄어드는 추세 |
| 검토 대기 | 검토 뒤 남은 항목 수 | 늘지 않음 |
| 결정 대기 응답 | 답한 결정 / 올라온 결정 | 80% 이상 |
